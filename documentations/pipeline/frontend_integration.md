# Plastic-Ledger: Frontend Integration Guide

This document outlines how the frontend application (and its associated backend/API) should interact with the Plastic-Ledger pipeline. It defines the command-line interface, expected arguments, and the resulting output artifacts that the frontend can consume to build the UI dashboard.

## 1. Executing the Pipeline

The pipeline is designed to be executed via a single Python entry point script. The frontend backend should spawn a child process to run this command.

### Base Command
```bash
python src/pipeline/run_pipeline.py \
    --bbox="-88.032,15.826,-88.012,15.846" \
    --date 2020-09-18 \
    --cloud_cover 20 \
    --no-bbox-filter \
    --backtrack_days 7 \
    --max_clusters 5
```

### Required Parameters
* `--bbox`: A bounding box in the format `min_lon,min_lat,max_lon,max_lat`. This defines the geographic area of interest (AOI) to search for marine debris.
* `--date`: The target date to search for Sentinel-2 imagery (format: `YYYY-MM-DD`).

### Performance & Optimization Flags
* `--cloud_cover`: Maximum allowable cloud cover percentage (e.g., `20`). Highly recommended to prevent the ML models from confusing clouds with debris.
* `--no-bbox-filter`: Bypasses strict geometric intersection filters. Usually recommended for coastal regions where precise intersections sometimes fail.
* `--backtrack_days`: **Critical for performance.** Determines how many days back in time the OceanParcels hydrodynamic simulation runs. A value of `7` is recommended for UI responsiveness. (Default without this flag is 30 days, which can take several minutes).
* `--max_clusters`: **Critical for performance.** Limits the number of debris clusters (ranked by area) that are processed through the heavy hydrodynamic backtracking simulation. A value of `5` is recommended.

## 2. Reading Pipeline Outputs

Once the pipeline completes successfully (exit code `0`), it generates a comprehensive suite of files inside the `data/runs/run_XXX/reports/<SCENE_ID>/` directory. The `<SCENE_ID>` is the Copernicus Sentinel-2 product ID (e.g., `S2B_MSIL2A_20200918T160839_N0500_R140_T16PCC_20230417T044949`).

The frontend should surface these generated artifacts to the user:

### Data & Metrics
* **`final_report.geojson`**: The primary data contract. A GeoJSON FeatureCollection containing polygons for every detected debris cluster. Each feature includes `properties` such as:
  * `area_m2`: Surface area of the plastic.
  * `mean_confidence`: Model confidence score.
  * `polymer_type`: Classified polymer material (e.g., "Marine Debris (Plastic)").
  * `source_type`: Attributed source of the debris (e.g., "Shipping Route").
  * `attribution_score`: Confidence in the source attribution.
  * `explanation`: Human-readable text explaining the attribution logic.
* **`debris_summary.csv`**: A flat tabular version of the GeoJSON data, perfect for rendering data tables or allowing the user to "Export as CSV".

### Visualizations & Maps
* **`backtrack_map.html`**: A standalone, interactive Leaflet HTML map. This file contains the complete interactive UI for exploring the detailed particle trajectories (curved paths) generated by the hydrodynamic simulation. **Integration:** Embed this file directly into the frontend using an `<iframe>`.
* **`rgb_map.png`**: A high-resolution RGB image generated directly from the Sentinel-2 B04, B03, B02 bands, cropped to the user's bounding box. The detected marine debris clusters are highlighted in vibrant red (`#FF0000`). **Integration:** Display in an image modal or hero section.
* **`polymer_distribution.png`**: A pie chart showing the breakdown of detected polymer types.
* **`detection_map.png`**: A scatter map of the debris clusters.

### Downloadable Report
* **`final_report.pdf`**: A polished, multi-page executive summary PDF containing all maps, charts, tables, and attribution explanations. **Integration:** Provide a "Download PDF Report" button in the UI that serves this file.

## 3. Handling Progress & State

The pipeline logs its progress to `stdout` using the `rich` Python library. It prints distinct stage headers:
* `━━━ Stage 1: Data Ingestion ━━━`
* `━━━ Stage 2: Preprocessing ━━━`
* `━━━ Stage 3: Debris Detection ━━━`
* `━━━ Stage 4: Polymer Classification ━━━`
* `━━━ Stage 5: Hydrodynamic Back-Tracking ━━━`
* `━━━ Stage 6: Source Attribution ━━━`
* `━━━ Stage 7: Report Generation ━━━`

The frontend backend can parse these `stdout` streams in real-time to update a progress bar or loading state in the user interface (e.g., "Step 5 of 7: Simulating Ocean Currents...").
